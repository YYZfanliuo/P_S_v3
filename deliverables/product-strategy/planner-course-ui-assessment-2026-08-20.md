# 计划中心、日程与课程表专项评估

日期：2026-08-20
版本：v1.7.0
范围：计划中心、日程管理、课程表视图、长期使用与 UI 方向

## 一、结论

当前版本可以作为“计划 AI 的安全流程原型”，但还不能作为完整的长期规划工具使用。

最关键的三个事实：

1. 计划生成器目前只生成一组固定的短期任务，任务全部使用同一个截止日期；“每天可用时间”只被显示，没有参与计算。
2. “允许调整日程”权限已经出现在界面，但当前应用计划时只写入 `data.todo`，没有写入 `data.schedule`。
3. 课程表周视图目前是七列课程卡片，不是按时间轴定位的课表；它能看出每天有什么课，但不容易看出一天的时间结构和空档。

因此，不建议现在做一次全面视觉改版。更应该先做一次“时间与计划结构升级”，UI 只围绕新结构调整。

## 二、问题 1：目前是否只会制作“今日”规划

### 判断：基本是，但更准确地说是“短期任务草案”，不是长期规划

代码证据：

- `scripts/app.js:624-636` 的 `plannerBuildDraft()` 固定生成 4 项任务：确认交付清单、整理材料、完成初稿、校对提交。
- 四项任务的 `dueDate` 都直接使用同一个目标截止日期，没有阶段日期、周日期或小时级时间块。
- `available` 仅保存并展示“每天可用时间”，没有用于计算剩余容量、排程压力或每日分配。
- `scripts/app.js:638-647` 的 `plannerApplyDraft()` 只把任务写入 `data.todo`，没有建立目标、里程碑、交付物和任务之间的关系。
- 当前智能模式只是静态展示待追问项目，并未形成可恢复的问答状态机或真正的动态规划。

### 对三下乡项目的直接影响

输入“8 月 25 日前完成三下乡项目”后，系统可以给出任务名称，但不能可靠回答：

- 今天做什么；
- 明天做什么；
- 主报告和附件分别哪天完成；
- 每天 2 小时是否够用；
- 某项延期后，后续任务如何整体顺延；
- 截止日前需要预留多少提交缓冲。

### 应有的数据层级

```text
目标 Goal
  → 阶段 Milestone
    → 交付物 Deliverable
      → 任务 Task
        → 时间块 ScheduleBlock
```

建议至少支持三种时间尺度：

- 长期：目标、截止日期、阶段和里程碑；
- 中期：月/周计划、交付物、任务依赖；
- 短期：今天、当前时段、下一步行动。

## 三、问题 2：是否能够写入日程时间表

### 判断：目前不能，权限是“预留接口”，不是已完成能力

代码证据：

- `plannerState()` 中存在 `writeSchedule` 权限字段。
- 计划中心界面存在“允许调整日程”复选框。
- 但 `plannerApplyDraft()` 实际只执行：

```js
 data.todo.unshift(...)
```

- 没有对应的：

```js
 data.schedule.unshift(...)
```

- 也没有生成日期、开始时间、结束时间、冲突检查或日程块。

### 当前风险

用户如果勾选“允许调整日程”，容易理解为 AI 会把计划排进时间表；但当前版本不会这样做。这属于**界面承诺与实际行为不一致**，应在下一版修复。

### 正确的写入流程

不建议 AI 直接把任务静默写进日程，应采用：

```text
任务草案
  → 计算可用时间
  → 生成时间块
  → 检查课程/已有日程冲突
  → 展示新增、移动、被挤出的事项
  → 用户确认
  → 自动快照
  → 写入日程
```

第一版排程规则可以先不接 AI：

- 排除课程表时间；
- 排除已有日程；
- 按每天可用时间分配；
- P0 任务优先；
- 截止日前预留提交缓冲；
- 冲突时不自动覆盖原日程，只提示用户选择。

## 四、问题 3：UI 是否需要大改，是否适合长期使用

### 判断：不建议全面推翻，但计划中心需要结构性改造

现有 UI 审美和个人工作逻辑不需要被抹掉。问题不在于颜色、背景、卡片风格，而在于当前界面没有把“长期目标 → 当前行动”的时间层级表达出来。

### 不建议现在做的事

- 不建议全面更换主题和视觉风格；
- 不建议把首页改成普通待办软件；
- 不建议删除课程、记账、习惯等个人系统模块；
- 不建议先做大量动画、背景和装饰；
- 不建议在没有真实计划数据前就做复杂 AI 面板。

### 必须做的结构调整

计划中心应从当前的“输入目标 → 生成四项草案”升级为：

1. **目标区**：目标、截止时间、成功标准、当前进度；
2. **阶段区**：里程碑、交付物和依赖关系；
3. **时间区**：周/月安排、每日可用容量和已占用时间；
4. **当前区**：今天要做什么、下一步是什么、预计用时；
5. **影响区**：完成/延期后会影响哪些计划；
6. **保护区**：变更预览、快照、撤销和恢复。

### 长期使用适配度

| 维度 | 当前判断 | 说明 |
|---|---|---|
| 个人日常记录 | 可以长期使用 | 现有模块和审美已经符合用户习惯 |
| 查看今天课程和日程 | 基本可以 | 日程有日/周/月，课程可查看当天和周卡片 |
| 长期目标管理 | 不足 | 尚无目标—里程碑—交付物关系 |
| 自动拆解与排程 | 不足 | 当前为固定规则草案，不计算容量 |
| 计划写入时间表 | 未完成 | 权限存在，但未写入 `data.schedule` |
| 延期后的全局重排 | 不足 | 无依赖、版本和影响分析 |
| 长期稳定使用 | 有潜力但需补底座 | 核心问题是计划结构，不是视觉风格 |

## 五、问题 4：课程周视图是否应改成时间表

### 判断：建议改，而且优先级较高

当前课程周视图的优点是简单，能快速知道每天有哪些课；但它的缺点也很明显：

- 课程按天堆叠，时间位置不直观；
- 无法快速看出课程之间的空档；
- 无法与今日日程对照；
- 课程时长和重叠关系不够明显；
- 手机端需要横向滚动七列，查看成本较高。

### 推荐形态：按时间轴的周课程表

```text
时间     周一       周二       周三       周四       周五
08:00              高数       英语
09:00   马原                  实验
10:00              ─空档─     ─空档─
11:00   课程                  课程
...
```

数据已经具备改造基础：课程记录已有星期、开始时间、结束时间、起止周和单双周字段。主要工作是把当前 `renderTimetableWeekView()` 从“七列卡片”改成“时间纵轴 + 七天横轴”的网格。

### 课程表与日程应如何分工

不建议把两者简单合并成一个模块：

- 课程表：固定、重复、不可随意覆盖的时间约束；
- 日程表：用户可安排和调整的时间块；
- 计划中心：根据课程表和日程表计算可用时间，并提出安排。

推荐在周时间表中提供图层或筛选：

- 仅课程；
- 课程 + 日程；
- 课程 + 日程 + 计划任务；
- 只看空闲时间。

课程块和计划块使用不同视觉编码，避免用户误以为课程可以被 AI 移动。

## 六、建议的实施顺序

### P0：先修正逻辑承诺

1. 将“允许调整日程”改为未完成能力提示，或真正实现最小日程写入；
2. 让计划草案区分“长期计划、近期计划、今日行动”；
3. 建立 Goal、Milestone、Deliverable、Task、ScheduleBlock 的 ID 关系；
4. 明确每天可用时间的格式和计算规则；
5. 生成计划时显示假设、容量和风险，而不是只显示 4 条固定任务。

### P1：实现时间排程

1. 生成周计划；
2. 根据课程表和已有日程计算空闲时段；
3. 生成日程时间块；
4. 预览冲突和变更；
5. 确认后快照并写入；
6. 完成或延期后提供局部重排，而不是覆盖全局。

### P1：改造课程周视图

1. 时间轴周表；
2. 当前时间线；
3. 课程块显示地点和课程名称；
4. 课程与日程叠加开关；
5. 移动端按“单日时间表”为默认，周表横向查看。

### P2：再做视觉增强

- 时间规划可视化风格；
- 背景、时钟壁纸；
- 计划负荷热力；
- 周复盘和趋势摘要。

## 七、最终判断

当前版本不是不能长期使用，而是：

> **记录系统可以长期使用，规划系统还没有完成。**

最重要的下一步不是“大改 UI”，而是补上“长期目标—中期计划—今日行动—时间块—全局反馈”这一条真实数据和交互链路。课程表则应优先改成时间轴周表，因为它是计划 AI 计算时间约束的基础。
