# 个人工作台 v1.6.0 功能易用性评估

> 评估日期：2026-08-19
> 范围：首次使用、首页、导航、记录、新建/编辑、日程/课程表、数据管理、同步、移动端
> 方法：只读审查项目文档、入口页面、核心脚本与桌面/移动端样式；未替代真实用户可用性测试

## 一、结论

当前产品“功能可用”，但还没有达到“对普通用户足够省心”的程度。

- **熟悉产品后**：日常记录、打卡、进度更新和首页查看相对顺手。
- **第一次使用**：模块较多、导航层级较深、示例数据较多，用户不容易理解先做什么。
- **高频操作**：快速记录入口是优点，但仍会进入完整编辑弹窗，记录链路没有真正压缩到最短。
- **复杂操作**：日程、课程表、同步和导入导出对非技术用户明显偏复杂。
- **移动端**：基础布局和弹窗适配不错，但主要依赖左上角菜单；项目总结中提到的底部导航在当前入口代码中没有实现。

综合判断：**易用性约 6/10；适合个人自己使用，不适合未经引导直接交给大量普通用户。**

## 二、优点

1. **首页有明确的“今天”入口**：今日计划、日程、课程、进度和快速记录被集中展示，符合“打开后先看今天”的定位。
2. **快速记录入口明确**：首页提供“记运动、记打卡、记一笔、记想法”，代码位于 `scripts/app.js:44-50`、首页绑定位于 `scripts/app.js:884`。
3. **记录类型统一**：todo、checkin、progress、finance、note 等模块共用新建/编辑机制，用户学会一种卡片操作后可迁移到其他模块。
4. **搜索支持中文输入法**：搜索框处理了 `compositionstart/compositionend`，避免中文输入过程中列表反复刷新，见 `scripts/app.js:1341-1346`。
5. **移动端弹窗考虑了手机场景**：底部弹窗、安全区、较大的输入控件和始终显示卡片操作，见 `styles/mobile.css:319-356`、`styles/mobile.css:267-271`。
6. **有导出、导入和删除确认**：基础数据可迁移，危险操作有确认提示。

## 三、影响最大的易用性问题

### P0：首次使用没有清晰的最短路径

**事实依据**：
- 产品包含 12 个模块，导航分为“今日行动、打卡追踪、内容记录、统计、其他”，见 `scripts/app.js:2268-2287`。
- 首次加载会自动注入各模块 seed 示例数据，见 `scripts/app.js:248-250`；配置中多个模块带有示例记录，见 `scripts/app.js:54-119`。
- 文档只建议“先看首页”，没有明确的 3 分钟引导、首次任务或“哪些模块可以暂时不使用”。

**用户影响**：用户可能误把示例数据当成自己的数据，也可能面对 12 个入口不知道从哪里开始。首页信息丰富，但首次打开时未必能马上感受到个人价值。

**建议**：
- 首次进入只引导完成一个闭环：创建今日任务 → 完成一次快速记录 → 回到首页查看反馈。
- seed 数据明确标注“演示数据”，提供“保留示例 / 清空示例”选择。
- 首次只突出 3-5 个核心模块，其余放入“更多功能”或允许关闭。
- 首页增加一个可关闭的“开始使用”引导卡，而不是依赖外部使用文档。

### P0：移动端导航与项目文档不一致

**事实依据**：
- `项目总结.md:155-161` 写有“底部导航栏（Tab Bar）”“左滑抽屉菜单”。
- 当前 `mobile.html:32-61` 只有顶部菜单按钮、抽屉和遮罩，没有底部导航 DOM。
- `scripts/app.js:2320-2337` 只绑定菜单按钮、关闭按钮和遮罩，没有左滑手势处理。
- 代码注释 `scripts/app.js:2306` 仍写“初始化日期标签、抽屉、FAB、底部导航”，但实际只初始化日期和抽屉；也没有看到 FAB 实现。

**用户影响**：用户会按照文档寻找底部导航或尝试左滑，但实际只能点击左上角菜单；这是明显的预期落差。

**建议**：二选一并保持一致：
- 推荐：保留抽屉，删除文档中“底部导航/左滑”的说法，并将菜单按钮说明写清楚；或
- 真正实现底部导航和左滑手势，并进行小屏实测。

### P1：快速记录只是“快捷打开完整表单”，没有真正降低记录成本

**事实依据**：
- 首页快速记录点击后执行 `go(...)` 和 `openEditor(...)`，见 `scripts/app.js:884`。
- 运动、记账、想法等弹窗仍包含多个字段；所有类型还统一追加“卡片样式”和“图片 URL”，见 `scripts/app.js:1662-1676`。

**用户影响**：用户想快速记一笔支出或打卡时，仍要面对完整编辑界面；高频记录容易被打断。

**建议**：
- 快速记录使用专用轻量表单：金额+分类、运动分钟数、打卡确认、想法正文，默认保存后关闭。
- “卡片样式、图片 URL”等低频字段移入“更多选项”，不要出现在普通记录路径。
- 支持保存后继续新增，适合连续记账或连续记录。

### P1：日程关联任务需要用户填写内部 ID

**事实依据**：
- 日程编辑器显示“关联模块”和“关联任务ID”，见 `scripts/app.js:1652-1654`。
- 项目交接说明将日程定位为日常行动入口，但当前关联方式要求用户知道记录 ID。

**用户影响**：普通用户不知道任务 ID 是什么，也不知道在哪里查；关联功能看似存在，实际难以使用。

**建议**：将“关联任务ID”改为可搜索的记录选择器：先选模块，再显示该模块的标题列表；保存后支持从日程跳回原任务。若暂时做不到，先隐藏该字段，避免暴露技术实现。

### P1：记录编辑器字段过多且缺少按场景收敛

**事实依据**：
- 课程表一次需要填写课程、教师、地点、星期、时间、起止周、单双周、不规则周、备注等字段，见 `scripts/app.js:1630-1640`。
- 日程需要日期、时间、关联、任务 ID、颜色、备注，见 `scripts/app.js:1641-1655`。
- 所有记录都追加卡片样式和图片 URL，见 `scripts/app.js:1662-1676`。

**用户影响**：新建记录时表单高度长、需要滚动；用户容易漏填、跳过或放弃。课程表和日程的专业字段没有区分“必填”和“高级设置”。

**建议**：
- 默认表单只保留完成首次记录所需字段。
- 高级字段折叠到“更多设置”。
- 用 `type="time"`、`type="date"`、下拉选择替代需要手写格式的字段；课程表当前 `startTime/endTime` 仍是普通文本输入，见 `scripts/app.js:1634-1635`。
- 明确必填项，并在保存前给出字段级错误，而不是静默兜底。

### P1：保存校验弱，错误会被静默变成“看似成功”的数据

**事实依据**：
- 通用标题为空时会保存为“未命名”，见 `scripts/app.js:1708`。
- 金额为空或非法时会变为 0，见 `scripts/app.js:1712`。
- 日程默认时间可直接保存；虽然会在时间输入变化时互相调整，但没有明确告诉用户发生了修正，见 `scripts/app.js:1684-1697`。
- 课程名称、地点、时间、周次没有完整的保存前校验，见 `scripts/app.js:1713`。

**用户影响**：用户以为保存成功，但之后看到“未命名”、¥0、空课程或异常日程；错误发现得晚，修复成本高。

**建议**：
- 标题、金额、日期、开始/结束时间、课程名称等按模块定义必填规则。
- 金额为空、负数或 0 时明确提示，而不是自动写入 0。
- 结束时间早于开始时间时阻止保存并说明原因。
- 保存成功后显示简短确认；失败时定位到具体字段。

## 四、其他重要问题

### P1：删除不可撤销，误操作恢复成本高

**事实依据**：记录删除提示明确写“此操作不可撤销”，见 `scripts/app.js:1746-1755`；重置同样不可撤销，见 `scripts/app.js:2123-2133`。

**用户影响**：手机上误触删除、批量整理时误删会造成焦虑；导入又会覆盖全部数据，恢复依赖用户此前是否导出过备份。

**建议**：先做低成本方案：删除后提供 5-10 秒“撤销”Toast；重置前强制导出一次或要求输入“重置”；导入前展示记录数量并要求确认。

### P1：模块多，但缺少隐藏/排序/场景模板

**事实依据**：项目总结把“模块自定义排序”列为后续优化，见 `项目总结.md:295-304`；当前导航由固定配置顺序生成，见 `scripts/app.js:2274-2287`。

**用户影响**：学生、自由职业者、普通生活记录用户看到的是同一套 12 模块，常用入口不一定靠前。

**建议**：增加“我的常用模块”或场景模板；支持隐藏不使用的模块和调整顺序。优先做隐藏/置顶，成本通常低于完整拖拽排序。

### P1：提醒、重复规则和系统快捷入口缺失

**事实依据**：项目总结将通知提醒列为后续优化，见 `项目总结.md:295-304`；当前核心代码未见日程通知或打卡提醒的实现。

**用户影响**：产品要求用户主动想起打开 App，难以形成每日使用习惯；日程管理目前更像查看工具，不是主动提醒工具。

**建议**：先做本地提醒实验：日程提醒、习惯提醒、日终复盘三类中只选一种，验证是否提升回访，再扩展系统通知。

### P1：同步对普通用户仍然过于技术化

**事实依据**：设置页要求填写 GitHub Token、Gist ID，并说明 Classic Token 和 gist 权限，见 `scripts/app.js:1874-1891`；帮助文档也要求用户配置并手动执行同步，见 `手机App使用文档.html:68-86`。

**用户影响**：非 GitHub 用户很可能在同步设置处流失；“自动同步”默认勾选，但首次仍需理解 Token、Gist 和连接/推送/拉取的区别。

**建议**：短期把同步步骤改成向导：备份说明 → 创建/连接 → 首次验证 → 显示“最后同步时间/当前设备”；长期改为账号托管同步。Token 不应成为大众用户的默认主路径。

### P2：桌面端和发布端代码存在差异，易造成体验不一致

**事实依据**：已对比 `scripts/app.js` 与 `www/scripts/app.js`，文件内容不完全一致；`index.html` 与 `www/index.html` 也不完全一致。

**用户影响**：桌面本地测试通过的交互，发布网页或 Android 包可能不同；用户反馈难以复现。

**建议**：建立单一源码/构建产物，或在发布前自动做双端一致性检查；至少把版本号、入口文件和脚本差异纳入发布清单。

## 五、按用户路径排序的改进顺序

### 第一优先级：让新用户 3 分钟内完成第一次成功体验

1. 首次引导和演示数据标识。
2. 移动端导航与文档统一。
3. 快速记录改成轻量表单。
4. 新建表单做必填校验。

### 第二优先级：降低日常维护成本

1. 日程关联改为标题选择器。
2. 删除撤销和导入前预览。
3. 模块隐藏/置顶或场景模板。
4. 选择一种本地提醒进行验证。

### 第三优先级：降低跨设备使用门槛

1. 同步向导和状态解释。
2. 备份/恢复演练和冲突提示。
3. 最终迁移到账号托管同步。

## 六、建议的可用性测试任务

找 8-10 名非项目维护者，分别使用手机和桌面端完成：

1. 第一次打开后，在 3 分钟内创建一个今日任务并完成一次快速记录。
2. 找到课程表并新增一门课，不看说明书。
3. 新增一笔支出并查看本月汇总。
4. 创建一个日程并关联一个已有任务。
5. 删除一条记录，再尝试恢复。
6. 导出数据，在另一设备导入并确认数据没有被误覆盖。
7. 找到同步入口，说出数据当前保存在哪里。

记录以下指标：任务完成率、完成时间、错误次数、求助次数、首次点击路径、主观难度 1-5 分。当前最值得重点验证的不是“用户喜不喜欢视觉”，而是“能不能在不看文档的情况下完成核心闭环”。

## 七、最终判断

产品现在不是不能用，而是“功能已经超过了引导和简化能力”。下一步不应继续增加模块，应该优先做：

> **减少首次选择、减少表单字段、减少技术术语、减少不可逆操作。**

如果只能先做三项，建议是：

1. 首次引导 + 演示数据明确标识；
2. 快速记录专用轻量表单；
3. 移动端导航/文档/实际代码统一。
